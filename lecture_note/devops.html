01 — DevOps란?

🚀 DevOps란?

DevOps는 Development(개발)와 Operations(운영)의 합성어입니다. 소프트웨어를 개발하는 팀과 운영·배포하는 팀이 하나의 문화와 자동화된 프로세스로 협력하는 방법론입니다.

📌 한 문장으로 정의하면?

"더 빠르게, 더 안정적으로, 더 자주 소프트웨어를 전달하기 위한 문화 + 자동화 + 도구의 조합"

🔍 DevOps를 구성하는 세 가지 핵심

🤝

문화 (Culture)

개발팀과 운영팀의 사일로(벽)를 허물고, 책임을 공유하는 협력 문화

⚙️

자동화 (Automation)

빌드·테스트·배포를 자동화하여 반복 작업을 없애고 실수를 줄임

🛠️

도구 (Tools)

Git, Docker, Kubernetes, Jenkins 등 자동화와 협업을 지원하는 도구들

💡 DevOps는 특정 기술이 아닙니다. 소프트웨어를 만들고 운영하는 방식에 대한 철학이자 문화입니다. 도구는 그 문화를 실현하는 수단입니다.

02 — 등장 배경

🏛️ DevOps가 등장한 이유

DevOps가 생겨나기 전, 소프트웨어 개발 현장에는 고질적인 문제가 있었습니다.

😰 전통적인 개발·운영의 문제

문제 개발팀 입장 운영팀 입장
목표의 충돌 빠르게 새 기능을 배포하고 싶다 안정성이 최우선, 변경은 위험하다
책임의 벽 "우리 환경에선 잘 됩니다" (개발 PC 기준) "서버에 올리면 왜 안 되지?" (운영 서버 기준)
느린 배포 주기 수개월 치 변경사항이 한 번에 배포 대규모 배포 = 대규모 장애 위험

💡 DevOps가 제시하는 해답

🔄 빠른 피드백 루프

작은 변경사항을 자주, 빠르게 배포하여 문제를 조기에 발견하고 빠르게 수정합니다.

🤖 자동화된 파이프라인

코드 변경의 빌드·테스트와 반복되는 배포 작업을 자동화하여 인적 실수를 줄입니다. 운영 배포의 승인 여부는 팀 정책에 따라 정합니다.

📦 환경의 일관성

Docker 같은 컨테이너 기술로 개발·운영 환경을 동일하게 유지하여 "내 PC에선 됐는데" 문제를 해결합니다.

03 — 혼자서도 DevOps

👨‍💻 소규모 개발자와 DevOps

DevOps는 대규모 팀만의 이야기가 아닙니다. 1~2인 소규모 개발자에게도 DevOps는 자연스럽게 필요해집니다.

🎯 소규모 개발자의 현실

💭 개발자의 바람

빠르게 새 기능을 개발하고 싶지만, 동시에 이걸 별 문제 없이 안정적으로 운영하고 싶은 욕구가 생깁니다.

인원이 적기 때문에 개발과 운영을 한 사람이 동시에 해야 하는 경우가 대부분입니다.

🛠️ 이를 위한 노력

🌿 브랜치 전략

개발용 브랜치와 운영용 브랜치를 분리하여 GitHub에서 관리합니다. 새 기능은 개발 브랜치에서 작업하고, 안정화된 코드만 운영 브랜치에 반영합니다.

📦 일관된 환경

Docker 등을 활용해 개발 환경과 운영 환경을 동일하게 유지합니다. "내 PC에선 되는데"라는 문제를 원천적으로 차단합니다.

🔄 자동화 파이프라인

반복 작업을 자동화하면 혼자서도 변경을 일관되게 검증하고 배포할 수 있습니다. 다음 슬라이드에서 CI/CD의 역할과 운영 배포 승인 차이를 살펴봅니다.

📋 체계적인 관리

소규모라도 버전 관리, 이슈 트래킹, 코드 리뷰 같은 체계를 갖추면 프로젝트의 품질과 유지보수성이 크게 향상됩니다.

💡 소규모 개발자일수록 DevOps의 자동화가 더 중요합니다. 인원이 적기 때문에 반복적인 수동 작업을 줄여야 개발에 집중할 수 있습니다.

04 — DevOps의 피드백 순환

♾️ 무한대 모양으로 이해하는 DevOps와 CI/CD

무한대(∞) 모양은 개발과 운영이 계속 연결되는 순환을 나타냅니다. 배포가 끝이 아니라, 운영에서 얻은 결과와 사용자 의견이 다음 개발 계획으로 돌아옵니다.

왜 필요할까요? 테스트만으로 실제 사용 환경의 모든 문제를 알 수는 없습니다. 운영 결과를 함께 살피고 작은 개선을 반복해야 사용자에게 필요한 서비스를 더 안정적으로 제공할 수 있습니다.

각 단계에서는 무엇을 하나요?

  1. 01 Plan · 계획사용자 의견과 운영 지표를 바탕으로 해결할 문제와 우선순위를 정합니다.
  2. 02 Code · 코드 작성작은 변경을 작성하고 Git·GitHub에서 리뷰하며 공유 코드에 자주 통합합니다.
  3. 03 Build · 빌드소스와 의존성을 실행 가능한 산출물이나 Docker 이미지로 만듭니다.
  4. 04 Test · 테스트자동 테스트로 변경이 요구사항을 충족하고 기존 기능을 깨뜨리지 않는지 확인합니다.
  5. 05 Release · 릴리스 준비검증된 버전과 배포 산출물을 확정하고 배포 가능한 상태로 준비합니다.
  6. 06 Deploy · 배포준비한 버전을 스테이징이나 운영 환경에 반영합니다.
  7. 07 Operate · 운영서비스를 유지하며 장애 대응, 용량 조정, 설정 관리 등을 수행합니다.
  8. 08 Monitor · 관찰로그·지표·알림과 사용자 반응을 살펴 개선할 문제를 Plan으로 전달합니다.

도구의 예로 Git·GitHub는 코드 협업, Jenkins는 빌드·테스트·배포 자동화, Docker는 이미지 생성, Kubernetes는 배포·운영에 활용할 수 있습니다. 도구 하나가 여러 단계에 걸쳐 쓰일 수 있습니다.

📌 핵심 정리

무한대 전체는 DevOps의 피드백 순환입니다. CI/CD는 그 안에서 변경을 빠르고 일관되게 검증·전달하도록 돕는 핵심 실천이며, 협업과 운영 피드백까지 포함하는 DevOps 전체와 같지는 않습니다.

참고: Atlassian — DevOps 수명주기와 피드백 · GitHub — Continuous integration

05 — CI와 두 가지 CD

🔄 CI와 CD는 무엇이 다를까요?

CI(Continuous Integration, 지속적 통합)는 코드 변경을 공유 코드베이스에 자주 통합하고, 자동 빌드·테스트로 검증하는 과정입니다. 작은 변경을 자주 확인하면 충돌과 오류를 일찍 발견하고 원인을 좁히기 쉽습니다.

CD는 문맥에 따라 Continuous Delivery(지속적 전달) 또는 Continuous Deployment(지속적 배포)를 뜻합니다. 둘 다 반복 가능한 배포 자동화를 활용하지만, 운영 배포를 시작하는 조건이 다릅니다.

↔ 표를 좌우로 밀어 세 가지 실천을 비교하세요.
구분CIContinuous DeliveryContinuous Deployment
목표변경을 자주 통합하고 오류를 조기에 발견검증된 변경을 언제든 배포 가능한 상태로 유지검증을 통과한 변경을 운영까지 자동 배포
주요 활동코드 통합 → 자동 빌드·테스트CI 이후 추가 검증 → 릴리스 준비 → 배포 가능한 산출물 유지CI와 추가 검증 → 운영 배포까지 자동 실행
운영 배포CI 자체가 운영 배포를 뜻하지 않음사람의 승인이나 배포 시점 결정 단계가 있을 수 있음각 변경에 대한 별도 수동 승인 없이 검증 통과 시 자동 배포
간단한 예수정 코드를 통합할 때 빌드와 테스트 실행검증된 버전을 준비하고 담당자 승인 후 배포 작업 실행검증된 버전을 파이프라인이 곧바로 운영에 배포

팀의 위험 관리·권한·환경 정책에 따라 승인 여부와 배포 대상이 달라집니다. Delivery의 승인은 배포 명령을 모두 손으로 실행한다는 뜻이 아닙니다. 두 CD는 폐기된 방식과 최신 방식의 구분도 아닙니다.

예시: 검색 기능을 개선했는데 응답이 느려졌다면?

  1. 1. 코드 수정검색 기능을 수정하고 공유 코드에 통합합니다.
  2. 2. 자동 테스트빌드와 기능 테스트를 실행해 변경을 검증합니다.
  3. 3. 배포Delivery라면 승인 후, Deployment라면 검증 통과 후 자동 배포합니다.
  4. 4. 문제 발견모니터링에서 실제 트래픽의 응답 시간 증가를 발견합니다.
  5. 5. 개선 ↺ Plan원인을 조사하고 쿼리 개선과 성능 테스트 추가를 다음 작업으로 계획합니다.

자동 테스트를 통과해도 운영의 모든 문제가 사라지지는 않습니다. 발견한 문제를 다음 계획과 테스트에 반영하면서 같은 순환을 반복합니다.

📌 핵심 정리

CI는 자주 통합하고 검증하기, Delivery는 언제든 배포할 준비 유지하기, Deployment는 검증된 변경을 운영까지 자동 배포하기입니다. 여기에 운영 결과를 다음 개발로 돌려주는 협업이 연결되어 DevOps의 순환을 이룹니다.

참고: GitHub — CI의 개념 · AWS — CI/CD와 운영 배포 승인 차이

06 — 협업을 위한 규칙

🤝 팀으로 일하기: 협업 규칙

같이 일하는 사람들과 미리 규칙을 정해두는 것이 중요합니다. 규칙 없이 협업하면 충돌과 혼란이 생깁니다.

📋 시작 전에 반드시 정해야 할 것들

📁 코드 관리 방법

  • 커밋 메시지 형식 (feat:, fix:, docs: 등)
  • PR(Pull Request) 리뷰어 지정 및 머지 기준
  • 코드 리뷰 최소 승인 수 결정
  • 공통 코딩 스타일 (린터, 포매터 설정 공유)

🌿 브랜치 관리 방법

  • main / master : 배포 가능한 안정화 코드만
  • develop : 개발 통합 브랜치
  • feature/기능명 : 기능 단위 개발 브랜치
  • 브랜치 네이밍 규칙과 삭제 시점 합의

⏱️ 2시간 규칙: 고민은 2시간을 넘기지 말 것!

  • 무엇을 하려 했는지, 어디서, 어떻게 시도해봤는지를 구체적으로 적어서 질문합니다.
  • 질문하는 것은 실력 부족이 아닙니다. 빠르게 막힌 것을 풀어야 개발이 진행됩니다.
  • 질문과 답변은 공유하여 같은 문제를 두 번 겪지 않도록 합니다.
  • AI가 방향을 제시해주기는 하지만 답은 되지 못할 수 있습니다.

🏢 사내 서비스는 우리가 아는 것과 다르게 동작한다!

  • 사내 보안 정책, 네트워크 설정, 프록시 등으로 인해 동작이 달라질 수 있습니다
  • 회사가 커스터마이징한 도구는 사외에서 사용하는 것과 다를 수 있습니다
  • 단순히 코딩 문제가 아니라 결재와 권한 문제일 수 있습니다.
  • 사내 문서, 기존 사례를 찾아보는 것도 좋지만 바뀌었을수도 있습니다.

✅ 좋은 협업은 기술보다 약속에서 시작됩니다. 규칙을 미리 정하고, 모르면 빠르게 물어보는 것이 좋습니다.
