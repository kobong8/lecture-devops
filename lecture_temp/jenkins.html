01 — Introduction

🔧 Jenkins란?

Jenkins는 소프트웨어 빌드, 테스트, 배포 과정을 자동화해주는 오픈소스 CI/CD 서버입니다. 2011년에 처음 등장한 이후 지금까지도 가장 널리 쓰이는 자동화 도구 중 하나입니다.

📌 한 문장으로 정의하면?

"개발자가 코드를 Push하면 자동으로 빌드 → 테스트 → 배포까지 실행해주는 로봇 같은 도구"

🔍 Jenkins가 하는 일

👀

코드 변경 감지

GitHub 등에 코드가 Push되면 자동으로 감지하여 파이프라인을 시작

🔨

자동 빌드

Maven, Gradle, npm 등으로 소스코드를 실행 가능한 형태로 빌드

🧪

자동 테스트

단위 테스트, 통합 테스트를 자동 실행하고 결과를 리포트로 제공

📦

이미지 패키징

테스트 통과 후 Docker 이미지를 빌드하고 레지스트리에 Push

🚀

자동 배포

Kubernetes 또는 서버에 새 버전을 자동으로 배포

🔔

결과 알림

성공/실패 여부를 Slack, Email 등으로 팀에게 즉시 알림

💡 Jenkins는 1,800개 이상의 플러그인을 지원합니다. GitHub, Docker, Kubernetes, Slack 등 거의 모든 DevOps 도구와 연동할 수 있어 DevOps 허브 역할을 합니다.

02 — Roles in CI/CD

🔄 CI/CD에서 Jenkins의 역할

CI/CD 파이프라인에서 Jenkins는 모든 단계를 연결하고 자동화하는 지휘자 역할을 합니다.

🏗️ CI/CD 파이프라인 전체 흐름

👨‍💻
개발자 → GitHub Push 개발자가 코드를 작성하고 git push로 GitHub에 올림. 여기서부터 자동화 시작.
↓ Webhook 트리거
🔧
Jenkins — CI 단계 (지속적 통합) 코드 체크아웃 → 빌드 → 단위 테스트 → 코드 품질 검사 순서로 자동 실행. 실패 시 즉시 알림.
↓ 테스트 통과 시
📦
Jenkins — Docker 이미지 빌드 & Push docker build로 이미지 생성 후 Registry에 Push. 태그는 Git 커밋 해시 등을 사용.
↓ 이미지 Push 완료
☸️
Jenkins — CD 단계 (지속적 배포) kubectl apply 등으로 Kubernetes 클러스터에 새 이미지 배포. 롤링 업데이트 수행.

📊 CI vs CD — 무엇이 다른가?

구분 CI (Continuous Integration) CD (Continuous Delivery/Deployment)
목적 코드 통합 오류를 빠르게 발견 언제든 배포 가능한 상태 유지
Jenkins 역할 빌드, 테스트 자동화 Docker 빌드, K8s 배포 자동화
실행 시점 코드 Push할 때마다 CI 성공 후 자동 또는 수동 승인
결과물 테스트 통과 여부 + 빌드 산출물 운영 서버에 새 버전 배포 완료
03 — Jenkinsfile Structure

📄 Jenkinsfile 구조 이해

Jenkins는 Jenkinsfile이라는 파일에 파이프라인 로직을 코드로 작성합니다. 이 파일은 프로젝트 루트에 위치하며, Pipeline as Code 방식으로 버전 관리가 가능합니다.

🏗️ 실무 표준 5단계 파이프라인 뼈대

pipeline { agent any environment { APP_NAME = 'fastapi-app' REGISTRY = 'registry.example.com' IMAGE_TAG = "${env.BUILD_NUMBER}" } stages { stage('① Checkout') { steps { /* 코드 가져오기 */ } } stage('② Build') { steps { /* 소스 빌드·패키징 */ } } stage('③ Test') { steps { /* 단위·통합 테스트 */ } } stage('④ Docker Push') { steps { /* 이미지 빌드 & 레지스트리 Push */ } } stage('⑤ Deploy') { steps { /* 서버/K8s에 배포 */ } } } post { always { /* 성공/실패 관계없이 항상 실행 (정리 작업) */ } success { /* 파이프라인 성공 시 실행 (알림 등) */ } failure { /* 파이프라인 실패 시 실행 (알림 등) */ } } }

📌 전체 단계 한눈에 보기

단계 역할 핵심 포인트
① Checkout 코드 가져오기 GitHub에서 최신 코드를 Jenkins 작업공간에 다운로드
② Build 소스 빌드·패키징 Maven / Gradle / npm 등으로 실행 가능한 형태로 컴파일·패키징
③ Test 자동화 테스트 단위·통합 테스트 실행 — 실패 시 이후 단계 자동 중단
④ Docker Push 이미지 빌드 & 배포 Dockerfile 기반 이미지 생성 → 고유 태그 + latest로 레지스트리에 Push
⑤ Deploy 서버/K8s 배포 kubectl apply 또는 ssh 배포로 새 이미지를 운영 환경에 반영
post 블록 후처리 성공/실패 알림, 임시 파일·이미지 정리 등 항상 실행
04 — Detail: Checkout

🔑 ① Checkout — 코드 가져오기

GitHub Webhook이 코드 Push를 감지하면 Jenkins가 자동으로 최신 코드를 다운로드합니다. 이 단계가 파이프라인의 출발점입니다.

stage('Checkout') { steps { // 방법 1 — 기본 (Public 저장소) git branch: 'main', url: 'https://github.com/myorg/my-app.git' // 방법 2 — credentialsId로 인증 (Private 저장소) checkout scm // Webhook에 연결된 저장소를 자동으로 사용 } }

📁 checkout scm 을 권장하는 이유

URL을 하드코딩하지 않고, Jenkins Job에 설정된 저장소 정보를 그대로 사용합니다. Webhook을 통해 자동으로 트리거된 브랜치·커밋을 정확히 체크아웃합니다.

🔐 Private 저장소 연결

Jenkins Credentials에 GitHub Token을 등록하고 credentialsId로 참조합니다. SSH Key 방식도 지원합니다.

💡 Checkout 후 Jenkins 작업공간

코드는 /var/jenkins_home/workspace/<JOB_NAME>/ 경로에 저장됩니다. 이후 모든 sh 명령어는 이 디렉터리를 기준으로 실행됩니다.

05 — Detail: Build

🔑 ② Build — 의존성 설치 · 패키징

Python/FastAPI는 컴파일 과정이 없으므로 Build 단계는 주로 가상환경 구성과 의존성 설치를 수행합니다. requirements.txt 또는 pyproject.toml을 기반으로 합니다.

stage('Build') { steps { // ① 가상환경 생성 및 의존성 설치 sh ''' python3 -m venv .venv . .venv/bin/activate pip install --upgrade pip pip install -r requirements.txt ''' // ② (선택) 정적 분석 — 코드 품질 검사 sh '. .venv/bin/activate && flake8 app/ --max-line-length=120' // ③ (선택) 타입 체크 sh '. .venv/bin/activate && mypy app/' } }

📁 FastAPI 프로젝트 기본 구조

fastapi-app/ ├── app/ │ ├── main.py # FastAPI 앱 진입점 │ ├── routers/ # 라우터 모듈 │ └── models.py # Pydantic 모델 ├── tests/ │ └── test_main.py # pytest 테스트 ├── requirements.txt # 의존성 목록 ├── Dockerfile └── Jenkinsfile

⚠️ requirements.txt는 버전을 고정(fastapi==0.111.0)해서 관리하세요. 버전 미고정 시 빌드 시점마다 의존성이 달라져 재현 불가능한 빌드가 됩니다.

06 — Detail: Test

🔑 ③ Test — pytest · 커버리지

FastAPI는 pytest와 httpx 기반의 TestClient로 엔드포인트를 테스트합니다. 이 단계 실패 시 Docker Push·Deploy는 자동으로 중단됩니다.

stage('Test') { steps { // pytest 실행 + JUnit XML 리포트 + 커버리지 측정 sh ''' . .venv/bin/activate pytest tests/ \ --junitxml=test-results.xml \ --cov=app \ --cov-report=xml:coverage.xml \ -v ''' } post { always { // JUnit 결과 → Jenkins 리포트 패널에 시각화 junit allowEmptyResults: true, testResults: 'test-results.xml' } } }

🧪 FastAPI TestClient 예시 (tests/test_main.py)

from fastapi.testclient import TestClient from app.main import app client = TestClient(app) def test_health_check(): res = client.get("/health") assert res.status_code == 200 assert res.json() == {"status": "ok"} def test_create_item(): res = client.post("/items", json={"name": "apple", "price": 1.5}) assert res.status_code == 201
🧪

단위 테스트

함수·유틸리티 단위 격리 테스트. pytest fixtures로 의존성 주입

🔗

통합 테스트

TestClient로 실제 HTTP 요청·응답을 DB 포함하여 검증

📊

커버리지

pytest-cov로 측정. coverage.xml을 Jenkins Cobertura 플러그인으로 시각화

07 — Detail: Docker Push

🔑 ④ Docker Push — 이미지 빌드 & 레지스트리 Push

테스트를 통과한 코드를 기반으로 Docker 이미지를 빌드하고 레지스트리에 Push합니다. 이 단계부터 배포 가능한 산출물이 만들어집니다.

stage('Docker Push') { steps { script { def fullImage = "${REGISTRY}/${APP_NAME}:${IMAGE_TAG}" // ① FastAPI 이미지 빌드 (빌드 번호를 ARG로 전달) sh "docker build --build-arg BUILD_NUM=${IMAGE_TAG} -t ${fullImage} ." // ② 레지스트리 로그인 (Credentials 사용) withCredentials([usernamePassword( credentialsId: 'registry-creds', usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS' )]) { sh "echo $REG_PASS | docker login ${REGISTRY} -u $REG_USER --password-stdin" } // ③ 버전 태그 Push (롤백용) sh "docker push ${fullImage}" // ④ latest 태그 Push (편의성) sh "docker tag ${fullImage} ${REGISTRY}/${APP_NAME}:latest" sh "docker push ${REGISTRY}/${APP_NAME}:latest" } } }

💡 왜 태그를 두 개 Push할까요?

태그예시목적
버전 태그my-app:42빌드 번호로 이전 버전 롤백 가능
latestmy-app:latest항상 최신 이미지를 쉽게 Pull
08 — Detail: Deploy

🔑 ⑤ Deploy — 서버 / Kubernetes 배포

레지스트리에 올라간 이미지를 실제 운영 환경에 반영하는 단계입니다. 배포 대상에 따라 방식이 달라집니다.

stage('Deploy') { steps { script { // ── 방법 A: Kubernetes (kubectl apply) ── sh """ kubectl set image deployment/${APP_NAME} \\ ${APP_NAME}=${REGISTRY}/${APP_NAME}:${IMAGE_TAG} \\ --record kubectl rollout status deployment/${APP_NAME} """ // ── 방법 B: Docker Compose (SSH 원격 배포) ── sshagent(['prod-server-key']) { sh """ ssh user@prod-server \\ "cd /app && docker compose pull && docker compose up -d" """ } } } }

☸️ Kubernetes 배포 포인트

kubectl set image로 Deployment의 컨테이너 이미지만 교체합니다. kubectl rollout status로 롤아웃 완료를 대기합니다. 실패 시 kubectl rollout undo로 롤백.

🖥️ SSH 배포 포인트

sshagent 플러그인으로 SSH 키를 안전하게 주입합니다. 원격 서버에서 docker compose pull 후 재시작하는 패턴이 가장 일반적입니다.

⚠️ 운영 배포 전 승인 게이트: 프로덕션 배포는 자동 실행 대신 input() 스텝으로 담당자의 수동 승인을 받는 것이 안전합니다.

input message: '프로덕션 배포를 승인하시겠습니까?', ok: '배포 진행'
09 — Detail: Post Actions

🔑 post — 후처리 블록

파이프라인이 끝난 후 항상 실행되는 블록입니다. 성공/실패/중단 등 상태별로 다른 동작을 정의할 수 있습니다.

post { always { // ① 항상 실행 — Docker 이미지 정리 (디스크 절약) sh "docker rmi ${REGISTRY}/${APP_NAME}:${IMAGE_TAG} || true" // JUnit 리포트 수집 (테스트 결과 시각화) junit allowEmptyResults: true, testResults: '**/test-results.xml' } success { // ② 성공 시 — Slack 알림 slackSend channel: '#deploy', color: 'good', message: "✅ 배포 성공: ${APP_NAME}:${IMAGE_TAG} (빌드 #${BUILD_NUMBER})" } failure { // ③ 실패 시 — 실패 URL 포함 알림 slackSend channel: '#deploy', color: 'danger', message: "❌ 파이프라인 실패: ${env.BUILD_URL}" } aborted { // ④ 수동 중단 시 slackSend channel: '#deploy', color: 'warning', message: "⚠️ 파이프라인 수동 중단: ${APP_NAME}" } }

📋 post 조건 종류

조건실행 시점
always성공/실패/중단 모든 경우에 실행 (정리 작업에 필수)
success파이프라인이 정상 완료된 경우에만
failure어느 Stage에서든 실패한 경우
aborted사용자가 수동으로 중단한 경우
unstable테스트 실패 등으로 UNSTABLE 상태가 된 경우
changed이전 빌드와 결과가 달라진 경우 (예: 실패→성공)
10 — Docker Management

🐳 Jenkins에서 Docker 이미지 관리

Jenkins 파이프라인에서 Docker 이미지를 빌드, 실행, 삭제하는 주요 명령어 패턴입니다.

🔨 빌드 (build)

sh "docker build -t fastapi-app:${IMAGE_TAG} ."

▶️ 실행 (run)

sh "docker run -d -p 8000:8000 fastapi-app:${IMAGE_TAG}"

🗑️ 삭제 (rmi)

sh "docker rmi fastapi-app:${IMAGE_TAG} || true"

📦 Dockerfile로 데이터 전달하기

방법명령어용도
--build-argdocker build --build-arg K=V빌드 시점 값 전달 (ARG 수신)
-edocker run -e K=V실행 시점 환경변수 전달 (ENV 수신)
11 — Dockerfile ARG

📋 FastAPI Dockerfile — ARG 활용

Jenkins에서 --build-arg로 전달한 값을 Dockerfile 안에서 ARG로 받아 사용하는 방법입니다. FastAPI 앱의 실제 Dockerfile 패턴을 기준으로 설명합니다.

# [Jenkinsfile] — 빌드 번호를 이미지에 기록 sh "docker build --build-arg BUILD_NUM=${BUILD_NUMBER} -t fastapi-app:${BUILD_NUMBER} ." # ────────────────────────────────────────────── # [Dockerfile] — FastAPI 멀티 스테이지 빌드 # ────────────────────────────────────────────── FROM python:3.11-slim AS builder WORKDIR /build COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt FROM python:3.11-slim ARG BUILD_NUM=dev ENV BUILD_VERSION=${BUILD_NUM} WORKDIR /app COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages COPY app/ ./app/ EXPOSE 8000 CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

💡 ARG vs ENV 차이

구분ARGENV
사용 시점빌드 시점실행 시점 (컨테이너 내부)
컨테이너 내 접근❌ 불가✅ 가능 (os.environ으로 읽기)
전달 방법--build-arg-e 또는 --env-file
FastAPI 활용버전 라벨, 빌드 시점 설정DB URL, SECRET_KEY 등 런타임 설정
12 — Auth in Docker Build

🔐 GitHub Token을 Docker로 전달

Private 저장소의 Python 패키지를 빌드 시 pip install로 설치해야 할 때, Jenkins Credentials를 안전하게 전달하는 패턴입니다.

// Jenkinsfile — Credentials를 --build-arg로 주입 withCredentials([usernamePassword( credentialsId: 'gh-creds', usernameVariable: 'GH_USER', passwordVariable: 'GH_TOKEN' )]) { sh "docker build --build-arg GH_TOKEN=${GH_TOKEN} -t fastapi-app:${IMAGE_TAG} ." } # Dockerfile — ARG로 토큰을 받아 pip 설치에만 사용 FROM python:3.11-slim AS builder ARG GH_TOKEN COPY requirements.txt . # Private 패키지를 GitHub 토큰으로 설치 RUN pip install --no-cache-dir \ -r requirements.txt \ git+https://${GH_TOKEN}@github.com/myorg/private-lib.git FROM python:3.11-slim # 최종 이미지에는 토큰이 남지 않음 COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages COPY app/ ./app/ CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

⚠️ 멀티 스테이지 빌드가 필수인 이유: ARG로 주입한 GH_TOKEN은 builder 스테이지 레이어에 남아 있습니다. 최종 이미지를 별도 FROM으로 분리하면 토큰이 포함된 레이어가 제외되어 이미지 히스토리에서 토큰이 노출되지 않습니다.

개발자는 코드와 설정 파일만 잘 작성하면, 나머지는 Jenkins가 처리합니다.

📥

① Checkout

GitHub에서 최신 코드를 가져오는 파이프라인의 시작점

🔨

② Build

가상환경 구성 + pip install로 의존성 설치, flake8/mypy 정적 분석

🧪

③ Test

pytest + TestClient로 엔드포인트 검증 — 실패 시 이후 단계 자동 중단

🐳

④ Docker Push

이미지 빌드 후 레지스트리에 버전 태그 + latest Push

🚀

⑤ Deploy

K8s / Docker Compose 등 운영 환경에 새 이미지 반영

📣

post 블록

성공/실패 알림 발송 및 임시 파일·이미지 정리

🎯 핵심 한 줄 요약: git push 한 번이면 Jenkins가 FastAPI 앱을 테스트하고 Docker 이미지로 빌드해 자동 배포합니다. 개발자는 비즈니스 로직에만 집중하세요.
