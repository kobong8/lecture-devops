01 — Kubernetes란 무엇인가

⎈Kubernetes란 무엇인가?

정의

Kubernetes(쿠버네티스, K8s)는 컨테이너화된 애플리케이션의 배포, 스케일링 및 관리를 자동화하는 오픈소스 컨테이너 오케스트레이션 플랫폼입니다.

⎈ Kubernetes 이름의 뜻

Kubernetes는 그리스어에서 유래한 이름으로, ‘키잡이’ 또는 ‘조타수’라는 뜻입니다. 배의 키를 잡고 방향을 조종하는 사람을 가리킵니다.

배의 항로를 유지하는 조타수에 비유하면, Kubernetes는 컨테이너화된 앱이 원하는 상태로 실행되도록 배치와 운영을 관리하는 역할을 합니다.

출처: Kubernetes 공식 문서 — 이름의 유래

💡 K8s의 의미

Kubernetes를 K8s로 줄여 쓰는 이유는 'K'와 's' 사이에 8개의 문자가 있기 때문입니다.

주요 기능

🔄 자동화된 배포와 롤백

애플리케이션 배포를 자동화하고, 문제 발생 시 이전 버전으로 즉시 롤백

📊 자동 스케일링

CPU, RAM 또는 커스텀 메트릭 기반으로 자동 확장/축소

🏥 자가 치유

실행에 실패한 컨테이너를 자동으로 재시작하고 교체

⚖️ 로드 밸런싱

트래픽을 여러 컨테이너에 분산하여 안정적인 서비스 제공

💡 핵심 컴포넌트 (직접구현할 경우)

Control Plane (마스터 노드)

  • API Server: 모든 요청의 진입점, kubectl과 통신하는 인터페이스
  • etcd: 클러스터의 모든 데이터를 저장하는 분산 키-값 저장소
  • Scheduler: 새로운 Pod를 어느 노드에 배치할지 결정
  • Controller Manager: 클러스터 상태를 관리하고 원하는 상태로 유지

Worker Nodes (워커 노드)

  • Kubelet: 각 노드에서 실행되며 Pod와 컨테이너 관리
  • Kube-proxy: 네트워크 규칙 관리 및 Pod 간 통신 지원
  • Container Runtime: 실제 컨테이너 실행 (Docker, containerd, CRI-O 등)
02 — 왜 Kubernetes가 필요한가

⎈왜 Kubernetes가 필요한가?

전통적인 배포 방식의 한계

과거에는 물리 서버에 애플리케이션을 직접 설치했습니다. 이는 리소스 할당 문제를 야기했고, 하나의 애플리케이션이 전체 서버 리소스를 독점할 수 있었습니다.

컨테이너의 등장과 한계

Docker와 같은 컨테이너 기술은 가볍고 이식성이 뛰어난 솔루션을 제공했지만, 프로덕션 환경에서 수백, 수천 개의 컨테이너를 관리하려면 오케스트레이션 도구가 필요했습니다.

Kubernetes가 해결하는 문제들

📦 대규모 컨테이너 관리

수백 개의 컨테이너를 자동화된 방식으로 관리

🌐 고가용성

애플리케이션이 항상 실행되도록 보장하고 자동 복구

🔄 무중단 배포

서비스 중단 없이 새 버전 배포 (Rolling Update)

💰 리소스 효율성

서버 리소스를 최적으로 활용하여 비용 절감

🌍 멀티 클라우드

AWS, GCP, Azure 등 어떤 환경에서도 동일하게 작동

📈 쉬운 확장

트래픽 증가에 따라 애플리케이션을 쉽게 확장

⚠️ 주의사항

Kubernetes는 강력하지만 복잡합니다. 소규모 프로젝트나 간단한 애플리케이션의 경우, Docker Compose나 다른 경량 솔루션이 더 적합할 수 있습니다.

03 — Docker와 Kubernetes의 관계

⎈Docker와 Kubernetes의 관계

역할의 차이

Docker와 Kubernetes는 함께 사용되지만, 각각 다른 역할을 수행합니다.

구분 Docker Kubernetes
주요 역할 컨테이너 생성 및 실행 컨테이너 오케스트레이션
범위 단일 호스트 클러스터 전체
자동화 제한적 완전 자동화
스케일링 수동 자동
복구 수동 자동 (Self-healing)

연동 프로세스

  1. 개발 단계: Dockerfile 작성 및 로컬에서 테스트
  2. 이미지 저장: Container Registry(Docker Hub, ECR, GCR 등)에 푸시
  3. Kubernetes 배포: Deployment YAML에서 이미지 경로 지정
  4. 컨테이너 실행: Kubernetes가 컨테이너 런타임을 통해 실행

💡 Container Runtime Interface (CRI)

Kubernetes는 Docker뿐만 아니라 containerd, CRI-O 등 다양한 컨테이너 런타임을 지원합니다. Docker로 빌드한 이미지는 여전히 사용할 수 있습니다.

04 — Image · Container · Pod 비교

⎈Image · Container · Pod 비교

Image는 실행에 필요한 패키지, Container는 그 이미지로 만든 실행 인스턴스, Pod는 Kubernetes가 컨테이너를 묶어 배치하는 최소 단위입니다.

구분 Image (이미지) Container (컨테이너) Pod (파드)
무엇인가? 앱 코드·라이브러리·실행 설정을 담은 읽기 전용 템플릿 이미지를 바탕으로 생성한 격리된 실행 환경 하나 이상의 컨테이너를 담는 Kubernetes 리소스
실행과 상태 자체적으로 실행되지 않는 배포 산출물 프로세스를 실행하며, 중지·종료 상태도 존재 컨테이너를 같은 노드에 함께 배치하는 단위
관계 이미지 하나로 여러 컨테이너 생성 가능 각 컨테이너는 사용할 이미지를 지정 보통 앱 컨테이너 하나, 필요하면 보조 컨테이너도 포함
예시 fastapi-app:v1
Python·FastAPI·앱 코드를 담아 빌드한 이미지		 이미지로 생성하고 Uvicorn으로 FastAPI 앱을 실행한 컨테이너 FastAPI 앱 컨테이너를 담은 api-1 Pod

같은 이미지로 Pod 두 개를 실행하면?

Image: fastapi-app:v1 (Python + FastAPI + 앱 코드) ├─ 이미지로 생성 → Pod api-1 [ FastAPI Container A ] └─ 이미지로 생성 → Pod api-2 [ FastAPI Container B ]

같은 이미지를 사용해도 각 컨테이너에서 FastAPI 앱이 별도로 실행됩니다. Kubernetes에서는 Pod 수를 늘려 앱의 실행 인스턴스를 확장합니다.

💡 Pod 안에서 공유하는 것

같은 Pod의 컨테이너는 IP와 포트 공간을 공유하고 localhost로 통신합니다. Pod에 정의한 볼륨을 각 컨테이너에 마운트하면 파일도 공유할 수 있습니다.

컨테이너마다 자체 파일시스템이 있으므로 Pod에 함께 넣는 것만으로 모든 파일이 공유되지는 않습니다.

05 — 쿠버네티스 오브젝트

⎈ 원하는 상태를 오브젝트로 표현하기

“쿠버네티스에서는 모든 것이 오브젝트다”는 입문용 표현입니다. 정확하게는 주요 관리 대상을 Kubernetes API 오브젝트로 표현합니다. YAML은 이 오브젝트를 만들거나 변경할 때 사용하는 선언 파일(매니페스트)의 한 형식입니다.

왜 필요할까요? 매번 서버에 명령을 내리는 대신 원하는 상태를 기록하면, 시스템이 실제 상태와 비교하며 차이를 줄일 수 있습니다.

오브젝트표현하는 대상범위
Pod함께 배치되는 하나 이상의 컨테이너와 실행 설정네임스페이스
DeploymentPod 복제본 수와 업데이트 방식네임스페이스
ServicePod 집합에 접근할 네트워크 엔드포인트네임스페이스
PV클러스터에서 사용할 실제 스토리지와 연결 정보클러스터 전체
PVC애플리케이션에 필요한 스토리지 요청네임스페이스

컨테이너 자체를 독립적인 Kubernetes API 오브젝트로 생성하지는 않습니다. 일반적인 앱 컨테이너 설정은 Pod의 spec.containers에 작성합니다.

YAML에서 읽어야 할 다섯 가지

필드의미예시
apiVersion사용할 API 그룹·버전Deployment는 apps/v1, Pod는 v1
kind오브젝트의 종류Deployment
metadata이름·네임스페이스·레이블 등 식별 정보name: demo-web
spec사용자가 선언한 원하는 상태replicas: 2
status시스템이 관측하고 갱신한 현재 상태readyReplicas: 1

여기서 다루는 Pod·Deployment·PV·PVC 등은 spec/status를 사용합니다. 모든 종류가 동일한 필드 구조를 갖는 것은 아닙니다. status는 보통 적용할 YAML에 직접 작성하지 않고 조회 결과에서 확인합니다.

예시: 웹 서버 Pod 두 개를 유지하고 싶다면?

Deployment YAML 예시 펼치기
apiVersion: apps/v1 kind: Deployment metadata: name: demo-web namespace: default spec: replicas: 2 selector: matchLabels: app: demo-web template: metadata: labels: app: demo-web spec: containers: - name: web image: nginx:1.28 # 환경: 이 이미지를 가져올 수 있어야 함
  1. 선언 · specPod 두 개를 원합니다.
  2. 관측 · status현재 준비된 Pod는 한 개입니다.
  3. 차이 확인·조정관련 컨트롤러가 상태를 비교하고 필요한 조치를 수행합니다.
  4. 다시 관측 ↺두 개가 준비됐는지 확인하고 계속 반복합니다.

예를 들어 관리 중인 Pod가 삭제되면 Deployment·ReplicaSet 컨트롤러가 함께 동작해 대체 Pod를 만듭니다. 단순히 준비되지 않은 Pod가 있다고 무조건 복제본을 늘리는 것은 아니며, 자원·이미지 등의 문제로 원하는 상태에 도달하지 못할 수도 있습니다.

📌 핵심 정리

오브젝트에 원하는 상태를 선언하면 컨트롤러와 관련 구성요소가 실제 상태를 관찰하며 맞춰 갑니다. 다음에는 스토리지 요청을 표현하는 PV와 PVC를 살펴봅니다.

공식 문서: Kubernetes 오브젝트와 spec/status · 컨트롤러

06 — PV와 PVC

💾 실제 스토리지와 사용 요청 분리하기

PV(PersistentVolume)는 실제 스토리지와 연결 정보를 나타내는 클러스터 범위의 오브젝트입니다. PVC(PersistentVolumeClaim)는 필요한 용량·접근 방식 등을 요청하는 네임스페이스 범위의 오브젝트입니다.

왜 필요할까요? 컨테이너의 쓰기 가능 계층에만 저장한 파일은 컨테이너가 교체되면 유지되지 않습니다. 앱의 실행 수명과 별도로 데이터를 보관하고, 스토리지의 구현과 사용 요청을 분리하기 위해 PV/PVC를 사용합니다.

  1. Pod · storage-demo같은 네임스페이스의 PVC 이름 demo-data를 참조합니다.
  2. PVC · demo-data조건에 맞는 PV 하나와 바인딩됩니다.
  3. PV · 클러스터 범위디스크·파일 공유 등의 실제 스토리지에 대한 정보를 가집니다.
  4. 실제 스토리지컨테이너의 /data에 마운트되어 파일을 보관합니다.

도식의 화살표는 참조·연결 관계입니다. 데이터가 PVC API 오브젝트를 통과한다는 뜻은 아닙니다. Pod는 디스크 종류·장치 ID 등의 세부 구현을 직접 지정하지 않아도 되지만, claimName, 볼륨 이름, mountPath는 설정해야 합니다.

접근 방식은 스토리지가 지원해야 합니다

방식의미알아둘 점
ReadWriteOnce · RWO한 노드에서 읽기·쓰기같은 노드의 여러 Pod가 사용할 수 있어 “Pod 하나만”이라는 뜻은 아님
ReadWriteMany · RWX여러 노드에서 읽기·쓰기이를 지원하는 파일 스토리지·드라이버가 필요

최소 예제: 1Gi 요청을 /data에 연결하기

기존 실습 환경 중 단일 노드 Minikube의 Linux 컨테이너를 기준으로 합니다. 실행 중인 클러스터에서 standard StorageClass와 provisioner가 준비되어 있는지 먼저 확인합니다. 생성 원리는 뒤의 동적 프로비저닝 슬라이드에서 설명합니다.

kubectl config current-context kubectl get storageclass minikube addons list

환경 의존 항목: standard 이름, 지원 용량·접근 방식, 이미지 다운로드 권한. Minikube의 storage-provisioner·default-storageclass 상태를 확인하세요. kind·Docker Desktop·사내 클러스터에서는 출력된 StorageClass 이름과 관리자 정책에 맞게 변경합니다.

PVC와 Pod YAML · storage-demo.yaml로 저장
apiVersion: v1 kind: PersistentVolumeClaim metadata: name: demo-data namespace: default spec: storageClassName: standard # 환경 의존: 실제 StorageClass 이름 accessModes: - ReadWriteOnce resources: requests: storage: 1Gi --- apiVersion: v1 kind: Pod metadata: name: storage-demo namespace: default spec: containers: - name: app image: busybox:1.37 # 환경 의존: 이미지 다운로드 필요 command: ["sh", "-c", "sleep 3600"] volumeMounts: - name: data mountPath: /data volumes: - name: data persistentVolumeClaim: claimName: demo-data
kubectl apply -f storage-demo.yaml kubectl get pvc demo-data -n default kubectl wait --for=condition=Ready pod/storage-demo -n default --timeout=120s kubectl exec -n default storage-demo -- sh -c 'echo hello > /data/hello.txt' kubectl exec -n default storage-demo -- cat /data/hello.txt

PVC가 Bound, Pod가 준비 상태이면 파일 쓰기·읽기를 확인할 수 있습니다. 대기 시간이 초과되면 kubectl describe pvc demo-data -n default와 kubectl describe pod storage-demo -n default의 이벤트에서 원인을 확인합니다.

Pod 삭제와 PVC 삭제는 다릅니다

삭제 대상이 예제의 동작
Pod만 삭제별도로 만든 PVC와 PV는 유지됩니다. 새 Pod가 같은 PVC를 마운트하면 저장된 파일을 다시 사용할 수 있습니다.
PVC 삭제연결된 PV와 스토리지의 후속 처리는 Reclaim Policy에 따라 달라집니다.

Pod가 PVC를 사용하는 동안에는 삭제 요청을 해도 보호 장치 때문에 PVC 제거가 지연될 수 있습니다. 영구 볼륨도 백업은 아니며, 로컬 실습 클러스터·디스크 자체를 삭제하거나 잃으면 데이터가 손실될 수 있습니다.

📌 핵심 정리

Pod → PVC 참조 → PV 바인딩 → 실제 스토리지의 관계를 기억하세요. Pod를 삭제했다고 영구 데이터가 바로 삭제되는 것은 아닙니다.

07 — Reclaim Policy

🗃️ PVC 삭제 이후의 처리 정책

Reclaim Policy는 PVC가 삭제되어 PV가 해제됐을 때 PV와 실제 스토리지를 어떻게 처리할지 정하는 정책입니다. 단순히 “사용이 끝난 볼륨의 초기화 설정”이라는 뜻은 아닙니다.

왜 필요할까요? 더 이상 쓰지 않는 스토리지를 자동 정리할지, 데이터를 보존하고 관리자가 확인할지를 정해야 하기 때문입니다.

정책PV·실제 스토리지 처리재사용·주의점
RetainPV와 데이터·스토리지를 보존합니다. PV는 보통 Released 상태로 남습니다.관리자가 데이터 확인, 정리, 재사용 절차를 처리합니다. 새 PVC에 곧바로 자동 재할당되지 않습니다.
Delete지원되는 드라이버에서 PV 오브젝트와 연결된 실제 스토리지를 삭제합니다.데이터도 잃을 수 있습니다. 드라이버 처리와 보호 장치 때문에 즉시 완료되지 않을 수 있습니다.
Recycle
deprecated		지원되는 과거 플러그인에서 데이터를 기본 정리한 뒤 볼륨을 재사용하던 방식입니다.폐기 예정으로 표시된 과거 방식입니다. 신규 구성에 권장하지 않으며 공식 문서는 동적 프로비저닝을 권장합니다.
  1. PVC 삭제 요청사용 중이라면 제거가 지연될 수 있습니다.
  2. PVC 제거·PV 해제PV의 reclaim policy를 기준으로 후속 처리합니다.
  3. Retain / Delete관리자가 보존·정리하거나, 지원 드라이버가 스토리지를 삭제합니다.

예시: demo-data를 지우기 전에 확인하기

# demo-data 행의 VOLUME 열에서 연결된 PV 이름 확인 kubectl get pvc demo-data -n default # 위 이름의 PV 행에서 RECLAIM POLICY 확인 (조회 권한 필요) kubectl get pv

예를 들어 연결된 PV가 Retain이면 PVC를 삭제해도 스토리지가 보존됩니다. Delete이면 드라이버가 스토리지까지 삭제할 수 있으므로, 중요한 데이터는 삭제 전에 해당 PV의 실제 정책과 백업 여부를 확인해야 합니다.

📌 핵심 정리

판단 기준은 Pod가 끝났는지가 아니라 PVC가 제거된 뒤 PV를 어떻게 처리할지입니다. Retain은 백업을 대신하지 않으며, Delete의 실제 동작은 드라이버 지원에 달려 있습니다.

공식 문서: PV 회수 정책·Recycle deprecated · PV 정책 확인·변경

08 — 동적 프로비저닝

⚙️ PVC 요청에 맞춰 스토리지 만들기

프로비저닝은 사용할 자원을 준비하는 일입니다. 동적 프로비저닝에서는 PVC 요청에 따라 provisioner가 실제 스토리지와 PV를 생성합니다. 요청마다 관리자가 디스크와 PV를 직접 준비하는 반복 작업을 줄입니다.

구분정적 프로비저닝동적 프로비저닝
누가 언제 준비?관리자가 실제 스토리지와 PV를 미리 준비PVC 요청을 바탕으로 provisioner가 스토리지와 PV를 생성
PVC 연결용량·접근 방식·클래스 등 조건이 맞는 기존 PV에 바인딩선택한 StorageClass로 생성한 PV에 바인딩
필요한 준비실제 스토리지, PV 정의, 접근을 지원하는 드라이버적절한 StorageClass, 동작하는 provisioner·드라이버, 생성 권한과 자원

StorageClass는 생성 방법과 정책을 선택합니다

StorageClass는 provisioner, 스토리지별 매개변수, 회수 정책, 바인딩 시점 등을 정의하는 클러스터 범위 오브젝트입니다. PVC의 storageClassName은 사용할 클래스를 지정합니다. 클래스 자체가 데이터를 저장하거나 디스크를 생성하는 프로그램은 아닙니다.

  1. 1. PVC 요청용량·접근 방식과 storageClassName 지정
  2. 2. 클래스·provisioner선택한 클래스의 설정을 읽고 생성 처리
  3. 3. 스토리지·PV 생성실제 저장 공간과 이를 나타내는 PV 준비
  4. 4. PVC 바인딩요청과 PV 연결
  5. 5. Pod 사용PVC를 참조한 볼륨을 컨테이너에 마운트

WaitForFirstConsumer 클래스는 PVC만 만들었을 때 생성을 기다릴 수 있습니다. 이를 사용하는 Pod의 배치 조건을 확인한 뒤 프로비저닝·바인딩하므로, 위 도식은 논리적 흐름이며 항상 PVC 생성 즉시 진행되는 것은 아닙니다.

예시: 앞의 standard는 무엇일까요?

# 클래스 이름과 provisioner, 정책, 바인딩 방식 확인 kubectl get storageclass kubectl get storageclass standard -o yaml

앞의 PVC 예제는 storageClassName: standard로 선택했습니다. 아래는 Minikube의 기본 hostPath provisioner 구성을 설명하기 위한 주요 필드 예시입니다. 기존 클래스를 덮어쓰는 실습이 아니며 실제 조회 결과를 기준으로 합니다.

apiVersion: storage.k8s.io/v1 kind: StorageClass metadata: name: standard provisioner: k8s.io/minikube-hostpath # 환경 의존: Minikube 기본 provisioner reclaimPolicy: Delete volumeBindingMode: Immediate

동적으로 생성된 PV는 생성 시 StorageClass의 reclaimPolicy를 물려받습니다. StorageClass에서 이를 생략하면 기본값은 Delete입니다. 이미 생성된 볼륨의 삭제 결과는 해당 PV의 spec.persistentVolumeReclaimPolicy를 확인해야 합니다.

📌 환경별 전제조건

  • PVC의 storageClassName을 생략하면 기본 StorageClass가 사용됩니다. 기본 클래스도 적합한 PV도 없으면 요청이 대기할 수 있습니다. storageClassName: ""는 생략과 달리 클래스 없는 PV를 요청하며 동적 프로비저닝을 끕니다.
  • 운영 환경은 보통 스토리지에 맞는 CSI 드라이버와 provisioner가 필요합니다. StorageClass YAML만 만든다고 드라이버가 설치되지는 않습니다.
  • Minikube의 기본 hostPath provisioner는 간단한 로컬 실습용이며 CSI 드라이버와는 다릅니다. 여기서는 단일 노드에 한정합니다. kind·Docker Desktop·사내 환경은 클래스와 지원 기능을 별도로 확인합니다.
  • 앞의 PVC가 Pending이면 클래스 이름, provisioner 상태, 용량·권한, volumeBindingMode와 Pod 생성 여부를 확인합니다.

📌 핵심 정리

PVC는 요청, StorageClass는 생성 방식·정책, provisioner는 실제 생성 담당입니다. 준비된 스토리지 환경이 있어야 자동으로 동작합니다.

공식 문서: 동적 프로비저닝 · StorageClass·기본 정책·바인딩 시점 · Minikube 기본 provisioner와 CSI의 차이

05 — Stateful vs Stateless 애플리케이션

⎈Stateful vs Stateless 애플리케이션

개념의 이해

Kubernetes에서 애플리케이션을 배포할 때 가장 중요한 결정 중 하나는 해당 애플리케이션이 상태를 유지해야 하는지 여부입니다.

구분 Stateless (무상태) Stateful (상태유지)
데이터 저장 인스턴스별 상태에 의존하지 않음 (외부 DB 저장 가능) 인스턴스의 상태·식별자와 저장 데이터 유지 필요
Pod 이름 (대표 컨트롤러 기준) Deployment: 생성 시 접미사 부여 (myapp-7d8f9-xyz) StatefulSet: 순번 기반 이름 유지 (mysql-0, mysql-1); 재생성 시 UID는 변경
스케일링 쉬움 (언제든 추가/제거) 복잡 (순서 보장 필요)
복제본 모두 동일 각각 고유한 상태
스토리지 불필요 또는 공유 각 Pod마다 전용
예시 웹 서버, API 서버 데이터베이스, 메시지 큐
06 — Deployment

⎈Deployment

정의

Deployment는 Pod의 배포를 관리하는 가장 기본적인 리소스입니다. ReplicaSet을 통해 지정된 수의 Pod 복제본을 유지하고, 롤링 업데이트와 롤백을 지원합니다.

주요 기능

🔄 롤링 업데이트

새 버전을 점진적으로 배포하여 무중단 업데이트

↩️ 롤백

문제 발생 시 이전 버전으로 즉시 복구

📊 복제본 관리

지정된 수의 Pod를 항상 유지

🔧 자동 복구

실패한 Pod를 자동으로 재생성

07 — Service

⎈Service

정의

Service는 Pod 집합에 대한 안정적인 네트워크 엔드포인트를 제공합니다. Pod는 언제든 재생성될 수 있고 IP가 변경되므로, Service를 통해 일관된 접근 방법을 제공해야 합니다.

🔗 Pod 간 통신은 어떻게 할까?

Pod는 생성될 때마다 새로운 IP를 받습니다. 따라서 직접 IP로 통신하면 Pod가 재시작될 때 연결이 끊깁니다. 이 문제를 Service가 해결합니다.

📌 핵심 원리: Label과 Selector

Service는 Label Selector를 사용하여 특정 Label을 가진 Pod들을 자동으로 찾아 트래픽을 전달합니다.

# Pod에 Label 부여 (Deployment에서 설정) labels: app: myapp ← 이 Label을 가진 Pod를 # Service가 Selector로 찾아서 연결 selector: app: myapp ← 자동으로 찾아 트래픽 전달

🌐 다른 Pod에서 접근하는 방법

같은 클러스터 내의 다른 Pod는 Service 이름으로 접근할 수 있습니다. Kubernetes가 자동으로 DNS를 생성해줍니다.

# 같은 네임스페이스 내에서 curl http://myapp-service:80 # 다른 네임스페이스에서 curl http://myapp-service.default.svc.cluster.local:80

Service 타입

타입 설명 사용 사례
ClusterIP 클러스터 내부에서만 접근 가능 (기본값) 내부 마이크로서비스 간 통신
NodePort 각 노드의 특정 포트로 외부 접근 가능 개발/테스트 환경
LoadBalancer 클라우드 로드밸런서 자동 생성 프로덕션 외부 노출 서비스

💡 Service Discovery

Kubernetes는 Service에 대해 자동으로 DNS 레코드를 생성합니다. Pod는 Service 이름만 알면 IP를 몰라도 통신할 수 있습니다.

형식: [서비스명].[네임스페이스].svc.cluster.local

08 — Ingress

⎈Ingress

정의

Ingress는 클러스터 외부에서 내부 서비스로의 HTTP/HTTPS 라우팅을 관리합니다.

하나의 IP 주소로 여러 서비스를 노출하고, 도메인 기반 라우팅, SSL/TLS 종료, 경로 기반 라우팅 등을 제공합니다.

⚠️ Ingress Controller 필요

Ingress 리소스를 사용하려면 Ingress Controller가 클러스터에 설치되어 있어야 합니다.

주요 Controller: NGINX, Traefik, HAProxy, AWS ALB, GKE Ingress

10 — kubectl describe

⎈🔍 상세 정보 확인

kubectl describe는 특정 리소스의 상세 정보와 이벤트 기록을 보여줍니다.

# Pod의 전체 이벤트와 상세 정보 확인 kubectl describe pod [Pod 이름] # 출력 내용: # - Pod가 어느 Node에 배치되었는지 # - 컨테이너 상태 (Running, Waiting, Terminated) # - 최근 이벤트 (스케줄링, 이미지 Pull, 실패 원인 등) # - 리소스 requests/limits

💡 describe는 장애 진단의 핵심 도구

Pod가 Pending이나 CrashLoopBackOff일 때, describe의 Events 섹션에서 원인을 파악할 수 있습니다.

11 — kubectl logs

⎈🔍 로그 확인

kubectl logs는 애플리케이션이 출력하는 로그를 확인하여 에러 원인을 진단합니다.

# Pod 로그 조회 kubectl logs [Pod 이름] # 실시간 로그 스트리밍 (-f = follow) kubectl logs -f [Pod 이름] # 크래시된 이전 컨테이너의 로그 kubectl logs [Pod 이름] --previous # 최근 1시간의 로그만 보기 kubectl logs [Pod 이름] --since=1h
12 — kubectl exec

⎈🔍 컨테이너 내부 접속

kubectl exec는 실행 중인 컨테이너 내부에 직접 접속하여 디버깅을 수행합니다.

# Pod 내부에 bash 셸로 접속 kubectl exec -it [Pod 이름] -- /bin/bash # Pod 내부에서 특정 명령어 실행 kubectl exec [Pod 이름] -- ls /app kubectl exec [Pod 이름] -- cat /app/config.yaml # 네트워크 연결 확인 (Pod 내부에서) kubectl exec [Pod 이름] -- curl http://other-service:80

🩺 장애 진단 체크리스트

Pod가 죽었을 때 확인 순서

  1. kubectl get pods → STATUS 확인
  2. kubectl describe pod [이름] → Events에서 원인 파악
  3. kubectl logs [이름] → 애플리케이션 에러 확인
  4. kubectl logs [이름] --previous → 크래시 전 로그 확인
  5. kubectl exec -it [이름] -- /bin/bash → 내부 직접 확인
13 — ConfigMap

⎈📄 설정 관리

ConfigMap은 환경 변수, 설정 파일 경로, 로그 레벨 등 민감하지 않은 데이터를 저장합니다.

apiVersion: v1 kind: ConfigMap metadata: name: app-config data: DATABASE_URL: "mysql://db:3306/mydb" LOG_LEVEL: "info" APP_MODE: "production"

💡 왜 사용하나요?

  • 코드 변경 없이 설정만 변경하여 재배포 가능
  • 환경별(dev/staging/prod) 다른 설정을 사용 가능
14 — Secret

⎈🔐 민감 정보 관리

Secret은 비밀번호, API 키, 토큰 등 외부에 노출되면 안 되는 데이터를 base64 인코딩하여 저장합니다.

apiVersion: v1 kind: Secret metadata: name: db-secret type: Opaque data: username: YWRtaW4= # base64("admin") password: cGFzc3dvcmQ= # base64("password")

📌 Pod에서 사용하는 방법

15 — 자주 발생하는 장애 사례 분석

⎈🚨 자주 발생하는 장애 사례 분석

kubectl describe pod에서 자주 만나는 장애 상황과 해결 방법을 알아봅니다.

1️⃣ 메모리 장애 — OOM과 퇴거를 구분

종료 이유와 이벤트를 먼저 확인하고, 앞 절의 메모리 장애 점검 순서로 원인을 좁힙니다. 컨테이너 재시작과 컨트롤러의 새 Pod 생성을 구분하세요.

2️⃣ CrashLoopBackOff — 반복 크래시

❌ 증상: Pod 안의 컨테이너가 반복 종료·재시작됨

$ kubectl describe pod myapp-pod State: Waiting Reason: CrashLoopBackOff ← 반복적으로 크래시 후 재시작 Restart Count: 5 Events: Warning BackOff Back-off restarting failed container

원인: 애플리케이션이 시작 직후 에러로 종료 → 재시작 → 또 종료 반복

해결:

  • kubectl logs [Pod이름] --previous로 크래시 전 로그 확인
  • 환경변수 누락, DB 연결 실패, 설정 파일 오류 등 확인

원인: 이미지 이름/태그 오타, Private 레지스트리 인증 실패, 이미지 미존재

15 — CPU·메모리 Requests와 Limits

📊 요청량과 사용 상한 구분하기

Requests는 스케줄러가 Pod를 어느 노드에 배치할지 판단할 때 사용하는 자원 요청량입니다. Limits는 실행 중 컨테이너에 적용할 사용 상한입니다. 두 값을 구분하면 배치할 자원과 실제 사용량을 함께 관리할 수 있습니다.

Requests: “적어도 이만큼 보장”만으로는 부족합니다

  • CPU request: 배치 판단에 쓰이며, CPU 경쟁 시 컨테이너에 CPU 시간을 배분하는 상대적 기준이 됩니다. 일반적인 공유 CPU 환경에서 특정 코어를 전용으로 할당한다는 뜻은 아닙니다.
  • Memory request: 주로 스케줄링과 노드의 메모리 압박 시 판단에 사용됩니다. 요청한 메모리를 앱이 미리 할당받아 항상 점유하는 것은 아닙니다.
  • Request는 실제 사용량이 아닙니다. 한가할 때는 적게 쓰고, 여유 자원과 limit 설정에 따라 request보다 더 사용할 수 있습니다. 메모리 request를 넘었다는 이유만으로 즉시 종료되지는 않습니다.

Limits: CPU와 메모리는 제한 방식이 다릅니다

CPU limit은 일정 기간에 사용할 수 있는 CPU 시간을 제한합니다. 할당된 시간을 다 쓰면 throttling(실행 억제·대기)이 발생합니다. Memory limit은 메모리 사용 상한이며, 초과 상황에서 커널이 프로세스를 OOM 종료할 수 있습니다. CPU처럼 시간을 나누어 기다리게 하는 방식이 아닙니다.

예시: 컨테이너 하나의 resources 설정

apiVersion: v1 kind: Pod metadata: name: resource-demo namespace: default spec: containers: - name: app image: busybox:1.37 command: ["sh", "-c", "sleep 3600"] resources: requests: cpu: "500m" memory: "1Gi" limits: cpu: "2" memory: "4Gi"

이 설정은 컨테이너별 spec.containers[].resources.requests와 resources.limits에 작성합니다. 예제는 자원을 소비하는 부하 테스트가 아니라 설정 위치를 보여줍니다.

단위읽는 방법예제의 의미
CPU · m1000m = 1 CPU, 500m = 0.5 CPU. 1 CPU는 환경에 따라 가상 코어 또는 논리 CPU에 해당합니다.요청은 0.5 CPU, 상한은 2 CPU
메모리 · Mi / Gi1Mi = 2²⁰ bytes, 1Gi = 2³⁰ bytes = 1024Mi. 십진 단위 M·G와 다릅니다.요청은 1Gi, 상한은 4Gi

기존 실습 환경의 Linux 컨테이너 기준입니다. Minikube·kind·Docker Desktop에 할당한 자원, 네임스페이스의 LimitRange·ResourceQuota, 이미지 접근 권한을 확인하세요. cgroup·런타임·CPU 관리 정책과 Windows 노드에서는 세부 동작이 달라질 수 있습니다. 이 예제는 기본적인 컨테이너별 설정을 사용합니다.

📌 핵심 정리

Request는 배치와 자원 배분의 기준, limit은 실행 중 상한입니다. CPU는 시간 제한, 메모리는 용량 제한이라는 차이를 기억하세요. 다음에는 같은 설정의 Pod 여러 개를 한 노드에 배치해 봅니다.

16 — Overcommit과 자원 경쟁

⚖️ 배치 가능과 동시 최대 사용은 다릅니다

Allocatable은 시스템용 예약분 등을 제외하고 Pod에 제공할 수 있는 노드 자원입니다. 일반적인 CPU·메모리 배치 판단에서는 이미 배치된 Pod와 새 Pod의 requests 합계를 allocatable과 비교합니다. 단순히 지금 측정한 사용량이 낮다고 계속 배치하지는 않습니다.

Overcommit은 여기서는 limits 합계가 allocatable보다 큰 설정을 말합니다. 실제 사용량이 서로 다른 시점에 증가한다면 자원을 효율적으로 쓸 수 있지만, 모든 컨테이너가 동시에 많이 사용하면 경쟁이나 부족이 발생합니다.

예시: CPU 4개·메모리 8Gi인 노드에 Pod 4개

각 Pod에 앞의 설정을 가진 앱 컨테이너가 하나씩 있다고 가정합니다. 표는 다른 Pod의 requests, init container, Pod overhead 등 추가 사용·요청을 제외한 단순 계산입니다. 실제 환경은 기존 Pod와 다른 배치 조건도 확인해야 합니다.

항목CPU메모리
노드 allocatable4 CPU8Gi
Pod 1개 request500m = 0.5 CPU1Gi
Pod 4개 requests 합계500m × 4 = 2000m = 2 CPU1Gi × 4 = 4Gi
Pod 1개 limit2 CPU4Gi
Pod 4개 limits 합계2 × 4 = 8 CPU4Gi × 4 = 16Gi
비교requests 2 ≤ 4, limits 8 > 4requests 4Gi ≤ 8Gi, limits 16Gi > 8Gi

이 가정의 자원 요청량 기준으로는 네 개를 배치할 수 있습니다. 하지만 노드 자원이 늘어나는 것은 아니므로, 네 개가 동시에 각각 2 CPU·4Gi를 모두 사용하는 것은 불가능합니다. limit은 그만큼의 용량을 노드에 예약하는 값이 아닙니다.

  1. 배치 전 · 스케줄러requests 합계와 allocatable을 비교합니다.
  2. 실행 중 · 실제 사용량 증가여유가 있으면 request보다 더 사용할 수 있습니다.
  3. 동시 사용 · 경쟁과 부족CPU 시간 배분·throttling, 메모리 OOM·eviction을 구분합니다.

자원이 부족해지면?

  • CPU 경쟁: 여러 컨테이너가 CPU 시간을 나누어 쓰므로 응답 지연이 커질 수 있습니다. 자신의 CPU limit에 도달하면 throttling이 발생하며, 이는 노드 전체가 한가해도 일어날 수 있습니다.
  • 메모리 부족: CPU처럼 단순히 사용 시간을 나눌 수 없습니다. 컨테이너 상한 초과 등에 따른 OOM 종료 또는 노드 압박을 완화하기 위한 kubelet의 Pod eviction(퇴거)이 발생할 수 있습니다.
  • 서로 다른 사건: OOM은 프로세스 종료이며 컨테이너가 OOMKilled로 보고될 수 있습니다. Eviction은 kubelet이 Pod를 종료하는 동작입니다. 노드 메모리가 부족하면 개별 컨테이너가 자기 limit 미만이어도 영향을 받을 수 있습니다. CPU 부족 자체가 OOMKilled의 원인은 아닙니다.

핵심 비교: CPU와 메모리

구분CPU메모리
Request스케줄링 기준 + 경쟁 시 CPU 시간 배분 기준스케줄링 기준 + 메모리 압박 시 사용량과 함께 판단
Request보다 더 사용여유 CPU와 limit 범위 내에서 가능여유 메모리와 limit 범위 내에서 가능
Limit일정 기간의 CPU 사용 시간 상한메모리 사용량 상한
경쟁·부족 시 동작CPU 시간을 나누어 지연 증가; limit 도달 시 throttling컨테이너 OOM 종료 또는 노드 압박에 따른 Pod eviction 가능

📌 핵심 정리 → 다음 주제: QoS

Requests에 맞춰 배치됐다고 모든 limit을 동시에 쓸 수 있는 것은 아닙니다. 다음 QoS 주제에서는 requests와 limits의 설정 조합으로 Pod가 어떻게 분류되는지 연결해 봅니다. 메모리 압박 시 처리에는 실제 사용량·requests·Pod 우선순위도 관여하므로, QoS 이름만으로 결과를 단정하면 안 됩니다.

17 — Pod QoS

🏷️ Requests·Limits에서 QoS로

QoS는 Quality of Service의 약자입니다. 기본적인 컨테이너별 설정에서는 CPU·메모리 requests와 limits의 조합으로 Pod 전체의 QoS 클래스가 결정됩니다. 자원 압박에 대한 동작을 이해하는 단서이며, 서비스 응답 속도나 무중단을 보장하는 등급은 아닙니다.

세 가지 클래스 비교

클래스조건예시
Guaranteed모든 컨테이너에 CPU·메모리 request와 limit이 있고, 각 자원의 request = limitCPU 100m / 100m, 메모리 64Mi / 64Mi
BestEffort모든 컨테이너에 CPU·메모리 request와 limit이 모두 없음resources 생략
Burstable위 두 조건에 해당하지 않음CPU 100m / 200m, 메모리 32Mi / 64Mi

일반 앱 컨테이너와 init container에 적용하는 기본 규칙입니다. 컨테이너 하나만 Guaranteed 조건을 만족해도 충분한 것은 아닙니다. 자원을 지정할 수 없는 ephemeral container는 이 조건의 대상이 아닙니다.

최소 예시: qos-demo.yaml

각 Pod는 컨테이너 하나로 구성됩니다. 세 예시를 한 파일로 저장하며, 앱은 대기만 합니다. 메모리 부족을 의도적으로 발생시키는 실습은 아닙니다.

apiVersion: v1 kind: Pod metadata: name: qos-guaranteed namespace: default spec: containers: - name: app image: busybox:1.37 command: ["sh", "-c", "sleep 3600"] resources: requests: {cpu: "100m", memory: "64Mi"} limits: {cpu: "100m", memory: "64Mi"} --- apiVersion: v1 kind: Pod metadata: name: qos-besteffort namespace: default spec: containers: - name: app image: busybox:1.37 command: ["sh", "-c", "sleep 3600"] --- apiVersion: v1 kind: Pod metadata: name: qos-burstable namespace: default spec: containers: - name: app image: busybox:1.37 command: ["sh", "-c", "sleep 3600"] resources: requests: {cpu: "100m", memory: "32Mi"} limits: {cpu: "200m", memory: "64Mi"}
kubectl apply -f qos-demo.yaml kubectl get pod qos-guaranteed qos-besteffort qos-burstable -n default -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass kubectl get pod qos-guaranteed -n default -o yaml

기존 Minikube 실습의 default 네임스페이스 기준입니다. LimitRange의 기본값이나 자동 주입된 사이드카가 있으면 실제 설정·분류가 달라질 수 있고, ResourceQuota 등 정책에 따라 생성이 거부될 수도 있습니다. limit만 지정하면 request가 같은 값으로 보완될 수 있으므로, 제출한 YAML뿐 아니라 생성된 Pod의 설정과 status.qosClass를 확인합니다.

확장 기능: Pod 수준 자원을 사용하는 경우

PodLevelResources를 지원·활성화한 클러스터의 spec.resources는 Pod 전체의 자원 예산입니다. 이 경우 Pod 수준 CPU·메모리 request/limit을 기준으로 QoS를 결정하는 별도 규칙이 적용되므로 위의 컨테이너별 표만으로 판단하지 않습니다. 예를 들어 Pod 수준에서 두 자원의 request와 limit이 각각 같으면, 모든 컨테이너에 개별 값을 적지 않아도 Guaranteed가 될 수 있습니다. 본문의 YAML은 이 기능을 사용하지 않습니다. 설치 버전과 기능 설정은 공식 문서에서 확인합니다.

📌 핵심 정리

QoS는 Pod의 자원 설정을 분류한 결과입니다. 앞 절의 resource-demo는 requests와 limits가 다르므로 Burstable입니다. 다음 절에서는 이 분류와 실제 종료·퇴거 판단을 구분합니다.

18 — OOM과 Eviction

🧠 무엇이, 누구에 의해 종료됐을까요?

OOM(Out Of Memory)과 eviction(퇴거)은 구분해야 합니다. 원인을 알아야 컨테이너 상한, 애플리케이션, 노드 용량 중 무엇을 고칠지 결정할 수 있습니다. 아래 설명은 기존 실습의 Linux 노드 기준입니다.

상황판단 주체·동작확인할 단서
컨테이너 cgroup OOM메모리 limit에 따른 제한 안에서 할당을 충족하지 못하면 커널이 프로세스를 종료할 수 있음컨테이너까지 종료되면 OOMKilled로 나타날 수 있음. 노드 전체에 여유가 있어도 발생 가능
시스템 OOM노드 전체 메모리가 부족하면 커널 OOM Killer가 프로세스를 선택해 종료노드·커널 로그와 컨테이너 상태를 함께 확인. 자기 limit 미만이어도 영향 가능
Node-pressure evictionkubelet이 메모리 압박 등을 감지해 자원을 회수하려고 Pod를 퇴거Pod의 Failed / Evicted 상태·이유와 이벤트, 노드 MemoryPressure 확인

QoS가 높으면 안전할까요?

일반적으로 BestEffort가 취약하고 Guaranteed가 상대적으로 보호됩니다. 그러나 Guaranteed도 자신의 메모리 limit에 따른 OOM이나 시스템 자원 부족에 따른 퇴거에서 면제되지 않습니다.

  • kubelet의 메모리 퇴거 판단: requests 초과 여부, Pod Priority, request 대비 사용량 등을 고려합니다. QoS 클래스 이름을 고정된 퇴거 순서로 사용하지 않습니다.
  • 커널의 시스템 OOM 판단: 프로세스의 메모리 사용량과 oom_score_adj 같은 보정값이 영향을 줍니다. kubelet이 QoS 등에 따라 이 값을 설정하지만, 이는 kubelet의 eviction 순위와 다른 판단입니다.

종료 뒤의 복구도 다릅니다

  1. OOM · 프로세스 종료컨테이너가 종료됐는지 확인합니다.
  2. kubelet · 재시작 판단restartPolicy 등에 따릅니다.
  3. 동일 Pod · 컨테이너 재시작Always / OnFailure 조건에 따라 재시작할 수 있고, Never이면 재시작하지 않습니다.
  1. Eviction · Pod 종료퇴거된 Pod가 그대로 다시 실행되는 것은 아닙니다.
  2. 컨트롤러 · 원하는 수 유지Deployment 등의 컨트롤러가 대체 생성을 담당합니다.
  3. 새 Pod · 다시 배치스케줄러가 배치합니다. 독립적으로 만든 Pod에는 자동 대체를 맡을 컨트롤러가 없습니다.

예시: Guaranteed Pod도 limit 64Mi에서 앱 메모리가 계속 증가하면 OOM을 겪을 수 있습니다. 반면 노드 압박으로 Deployment의 Pod가 퇴거되면 새 Pod가 생성됩니다. 두 경우 모두 메모리 누수나 용량 부족을 해결하지 않으면 문제가 반복될 수 있습니다.

📌 핵심 정리

커널 OOM은 프로세스 종료, kubelet eviction은 Pod 퇴거입니다. CPU 부족 자체가 OOMKilled를 일으키지는 않습니다. 컨테이너 재시작과 새 Pod 생성도 구분합니다.

공식 문서: 메모리 limit 적용 · 퇴거 판단·시스템 OOM · 컨테이너 재시작과 Pod 수명

19 — 메모리 장애 점검

🔎 상태 → 로그 → 사용량 → 원인

아래의 resource-demo와 컨테이너 app은 앞 절의 예제 이름입니다. 실제 장애를 조사할 때는 문제가 발생한 Pod·컨테이너 이름과 네임스페이스로 바꿉니다.

1. 종료 상태와 이벤트부터 확인

kubectl describe pod resource-demo -n default kubectl get events -n default --field-selector involvedObject.kind=Pod,involvedObject.name=resource-demo --sort-by=.metadata.creationTimestamp kubectl get pod resource-demo -n default -o wide

State, Last State, 종료 이유, 재시작 횟수와 이벤트를 봅니다. OOMKilled만으로 limit 초과인지 시스템 OOM인지 단정하지 않습니다. 종료 코드 137만으로도 OOM을 확정할 수 없습니다. Pod가 Evicted라면 퇴거 메시지와 당시 노드 상태를 확인합니다.

2. 직전에 종료된 컨테이너의 로그 확인

kubectl logs resource-demo -n default -c app --previous

--previous는 같은 Pod 안에서 이전에 종료된 해당 컨테이너 인스턴스의 로그입니다. 이전 인스턴스가 없거나 로그가 보존되지 않았으면 조회되지 않습니다. 대체 생성된 새 Pod에서 옛 Pod의 로그를 가져오는 명령은 아닙니다.

3. Pod 사용량과 노드 여유를 함께 확인

kubectl top pod resource-demo -n default --containers kubectl top node kubectl get nodes # NODE_NAME을 1단계에서 확인한 실제 노드 이름으로 바꿉니다. kubectl describe node NODE_NAME kubectl get events -A --field-selector involvedObject.kind=Node --sort-by=.metadata.creationTimestamp

kubectl top에는 Metrics Server 등 리소스 메트릭 제공 구성요소가 필요합니다. Minikube도 활성화 여부를 확인해야 합니다. 최근 측정값이므로 종료 직전의 순간 최대 사용량은 놓칠 수 있습니다. 모니터링 이력과 노드·커널 로그를 함께 보며, 노드 로그 접근 방식은 운영 환경과 권한에 따라 다릅니다.

4. 확인한 원인에 맞춰 대응

확인한 원인대응
메모리 누수·과도한 캐시앱의 메모리 증가 추세, 힙·캐시 설정을 점검하고 수정합니다. limit만 높이면 재발을 늦출 뿐일 수 있습니다.
정상 사용량과 설정 불일치실측 사용량과 순간 증가분을 고려해 requests/limits를 조정합니다. request는 배치에도 영향을 주므로 노드 여유를 함께 확인합니다.
노드 용량·배치 문제allocatable, requests 합계, 실제 동시 사용량, 시스템 예약분을 점검합니다. 과도한 밀집을 줄이거나 노드 용량을 늘립니다.
  1. 오브젝트원하는 상태를 선언합니다.
  2. 스토리지Pod → PVC → PV로 영구 저장소를 연결합니다.
  3. 자원 관리requests로 배치하고 limits로 상한을 설정합니다.
  4. QoS · 진단분류를 확인하고 OOM·퇴거의 원인을 구분합니다.

📌 핵심 정리

QoS 이름만 보고 limit을 올리지 말고 종료 주체·범위와 실제 사용량부터 확인합니다. Pod 종료·퇴거는 PVC 삭제와 다릅니다. PV의 Reclaim Policy를 OOM 복구 정책으로 해석하지 않습니다.

공식 문서: Pod 디버깅 · 이전 컨테이너 로그 · top과 메트릭 요구사항

17 — Kubernetes 핵심 정리

⎈🎯 Kubernetes 핵심 정리

1. Kubernetes란?

  • 컨테이너 오케스트레이션 플랫폼
  • 자동화된 배포, 스케일링, 관리
  • 고가용성 및 자가 치유

2. 핵심 리소스

Pod

가장 작은 배포 단위, 하나 이상의 컨테이너 그룹

Deployment

Stateless 애플리케이션 배포 및 관리

Service

Pod에 대한 안정적인 네트워크 엔드포인트

Ingress

HTTP/HTTPS 라우팅 및 SSL 종료

PV · PVC · StorageClass

스토리지를 나타내는 PV, 사용 요청인 PVC, 동적 생성 방식과 정책을 정하는 StorageClass

3. 기초 설계 원칙

  • ✅ 선언적 설정 (YAML 파일을 Git으로 관리)
  • ✅ 롤링 업데이트 전략 사용
  • ✅ Pod에 직접 접근하지 않고 Service를 통해 연결
  • ✅ 상태 데이터는 PVC로 연결한 볼륨 등 실행 수명과 분리된 스토리지에 저장
  • ✅ PVC 삭제 전에 PV의 Reclaim Policy와 데이터 백업 확인

4. 학습 로드맵

  1. 기초: Pod, Deployment, Service
  2. 오브젝트·스토리지: API 오브젝트 → PV·PVC → Reclaim Policy → 동적 프로비저닝·StorageClass
  3. 네트워킹: Service, Ingress
  4. 실무: ConfigMap, Secret, Requests/Limits·Overcommit, QoS·OOM·Eviction, 상태 확인, 로그 분석, 장애 진단
