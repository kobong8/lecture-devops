01 — 운영 관점에서 Pod 이해하기

Pod의 STATUS는 결과이고 원인은 아닙니다. 현재 상태, 컨테이너 상태와 Events를 차례로 확인해야 합니다.

상태의미다음 확인

kubectl get pods -o wide kubectl get pods -A kubectl get events --sort-by=.lastTimestamp
02 — kubectl 진단 도구

🩺 get → describe → logs → exec

증거 수집 순서

  1. get: 상태와 재시작 횟수 확인
  2. describe: 컨테이너 상태와 Events 확인
  3. logs: 애플리케이션 오류 확인
  4. exec: 살아 있는 컨테이너 내부 점검
exec부터 실행하지 않습니다. 크래시 중인 컨테이너에는 접속할 수 없고 상태를 바꿔 증거가 흐려질 수 있습니다.
kubectl describe pod myapp-pod kubectl logs myapp-pod --previous kubectl logs myapp-pod -c app --tail=100 kubectl exec -it myapp-pod -- sh kubectl exec myapp-pod -- curl -sS http://api:8000/health
03 — ConfigMap과 설정 주입

📄 이미지와 환경별 설정을 분리한다

apiVersion: v1 kind: ConfigMap metadata: name: app-config data: LOG_LEVEL: "info" DB_HOST: "postgres"
envFrom: - configMapRef: name: app-config # 특정 키만 선택할 때 env: - name: DB_HOST valueFrom: configMapKeyRef: name: app-config key: DB_HOST
운영 포인트: 환경변수로 주입된 값은 ConfigMap을 수정해도 실행 중인 프로세스에 자동 반영되지 않습니다. 설정 변경 후 Rollout 전략을 함께 설계합니다.
04 — Secret 안전하게 사용하기

🔐 Base64는 암호화가 아니다

apiVersion: v1 kind: Secret metadata: name: db-secret type: Opaque stringData: password: change-me
env: - name: DB_PASSWORD valueFrom: secretKeyRef: name: db-secret key: password
  • Secret YAML 원문을 Git에 커밋하지 않습니다.
  • RBAC으로 읽기 권한을 최소화하고 etcd 암호화를 검토합니다.
  • 운영에서는 Vault·클라우드 Secret Manager와 External Secrets 같은 연동을 고려합니다.
05 — Resource requests와 limits

📊 스케줄링 기준과 사용 상한을 정의한다

resources: requests: cpu: "500m" memory: "512Mi" limits: cpu: "1" memory: "1Gi"
설정운영 의미
CPU request스케줄러가 예약 기준으로 사용
CPU limit초과 시 throttling 가능
Memory request노드 배치 기준
Memory limit초과 시 OOMKilled 가능
requests를 과도하게 높이면 여유 자원이 있어도 Pod가 Pending이 될 수 있습니다. limits만 늘리기 전에 실제 사용량과 메모리 누수를 확인합니다.
06 — Startup Readiness Liveness Probe

❤️ 프로세스 생존과 서비스 준비는 다르다

Probe질문실패 시 동작
startup애플리케이션 시작이 끝났는가?성공 전 다른 Probe 대기
readiness지금 요청을 받을 수 있는가?Service Endpoint에서 제외

07 — 장애 대응 I

🧯 CrashLoopBackOff와 ImagePullBackOff

CrashLoopBackOff

  1. describe로 Exit Code 확인
  2. logs --previous로 직전 로그 확인
  3. 명령, 환경변수, 의존 서비스 점검
  4. Probe가 너무 공격적인지 확인

ImagePullBackOff

  1. 이미지 이름과 태그 확인
  2. Registry에 이미지 존재 여부 확인
  3. imagePullSecrets 확인
  4. 노드의 Registry 접근성 확인
kubectl describe pod myapp-pod kubectl logs myapp-pod --previous kubectl get secret regcred kubectl rollout status deployment/myapp

🚨 Pending OOMKilled Probe Failed PVC Pending

증상주요 원인핵심 확인

09 — HPA 자동 확장

📈 부하에 따라 Pod 수를 조절한다

HPA는 Metrics Server 등의 지표를 보고 Deployment의 replica 수를 조절합니다. CPU 사용률 계산을 위해 대상 컨테이너에 CPU request가 필요합니다.

kubectl autoscale deployment myapp \ --cpu-percent=60 --min=2 --max=5 kubectl get hpa -w kubectl top pods
평상시 2 Pods
↓ 부하 증가
5 Pods
↓ 안정화 기간
2 Pods
HPA는 즉시 반응하는 마법이 아닙니다. Metrics 수집 주기, 안정화 시간, 애플리케이션 시작 시간과 DB 같은 하위 시스템의 용량도 함께 고려합니다.
10 — 종합 장애 대응 실습

✅ 관찰하고 가설을 세우고 검증한다

장애 주입

  1. 존재하지 않는 이미지 태그 배포
  2. 필수 Secret 키 제거
  3. readiness 경로를 잘못 지정
  4. 과도한 memory limit 설정
  5. request를 높여 Pending 유도

완료 기준

  1. 증상과 영향을 설명한다.
  2. get·describe·logs로 증거를 남긴다.
  3. 원인 가설을 한 번에 하나씩 검증한다.
  4. 수정 후 Rollout과 Endpoint를 확인한다.
  5. 재발 방지 설정과 모니터링 항목을 제시한다.
운영 사고 과정: 상태 확인 → Events와 로그 수집 → 원인 가설 → 최소 변경 → 복구 검증 → 재발 방지
